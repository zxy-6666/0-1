# 排程逻辑对照：v1.0（上传版） vs 当前工作版

> 目的：逐文件、逐逻辑块说明两版差异，供决定保留哪个版本（或如何合并）。
> 数据文件（data/ 全部 17 个 CSV）两版**完全一致**，因此所有行为差异都来自代码。
> 行号为各文件内实际行号（左=v1.0，右=当前版）。

## 总览

| 文件 | v1.0 行数 | 当前版行数 | 差异规模 | 差异性质 |
|---|---|---|---|---|
| models.py | 223 | 224 | 1 行 | 新增 pioneer 字段 |
| data_loader.py | 934 | 962 | 34 行 | 「是否生效」列过滤 + pioneer 解析 |
| optimizer.py | 586 | 588 | 8 行 | 得分组合加 lead_back_to_back_term（现值恒 0） |
| validation.py | 441 | 512 | 93 行 | lead 闸B、先导批不计分、去掉 Q 缺口重罚 |

结论先行：**当前版 = v1.0 + 今天为满足你最新需求做的一批改动**。v1.0 是更早的稳定基线。

## 1) models.py

v1.0 `Lot` 无先导批概念；当前版在 `Lot` 上新增：

```python
pioneer: bool = False   # 先导批：跑在前面扫雷；完工时间不计入目标得分，Q-time 等硬约束仍生效
```

---

## 2) data_loader.py

v1.0：读 CSV 后原样返回。
当前版新增两处（均向后兼容，无该列时行为不变）：

1. **「是否生效」过滤**（`_apply_enable_filter`）：某行勾选被取消（存为 `0/否/n/no/false/off`）后加载即忽略，重新勾选即可恢复。数据管理界面功能。
2. **pioneer 解析**：`lot_list.csv` 存在 `pioneer` 列时，`true/t/y/yes/1` → `Lot.pioneer=True`。

---

## 3) optimizer.py

v1.0：`penal = score + qtime_margin_term`（加权完工 + Q 余量统一罚/奖）。
当前版：`penal = score + qtime_margin_term + lead_back_to_back_term`（SA 两层同改）。
→ 但当前版 validation 里 `lead_back_to_back_term` 恒为 0（见 §5），**这一处实际无效果**，属残留。

## 7) 若整体切 v1.0 —— 会丢失（对照你提过的需求）

1. **先导批**：f45/f678/f9 会被当普通批次计入完工得分、且被 lead 注入拖拽 → 实测 f45 从 09-07 拖到 09-13、出现 real4 反超先导批（闸A 2 例）——正是你最早投诉的现象。
2. **lead 1.5h 冗余带硬约束（闸B）**：v1.0 只有先后序（闸A），间隔 1.5h 上限完全不校验。
3. **纯完工时间目标**：v1.0 保留 Q 余量缺口 1e6 重罚 → 有“为攒余量把批次推后”的动机（你今天要求去掉）。
4. **「是否生效」行停用功能**：CSV 里取消勾选的行会被重新加载（数据管理界面功能失效）。
5. 今天排障中修的若干病态：紧链被粗排锚点钳进停机窗跨天、跨班次推后失效、中间步真实槽位低估、warning 刷屏。

## 8) 若保留当前版 —— v1.0 值得吸收的

- 整链块**不超Q是构造期硬目标**（v1.0 全程无超Q；当前版 real8 超 59min 说明构造期仍会破界）。
- v1.0 的 Q 余量罚分在优化器里的引导作用，可用**构造期三站联合预约（排 A 前查 B/C 真实槽位）+ 保留告警但不罚分**替代，正是待办 p2b。

## 9) 建议

- 两版在此算例上都不是全合法解；差异本质：**v1.0“Q 稳但不认识先导批”，当前版“先导批对但 Q 会破”**。
- 若你的真实场景里**先导批 + 1.5h lead 是硬需求** → 不应整体切 v1.0，建议：当前版为基，补“排 A 前看 B/C”构造期保底（吸收 v1.0 不超Q 的优点）。
- 若你的真实场景**没有先导批概念**（或可接受旧 lead 语义）→ 整体切 v1.0 风险小、收益直观。
