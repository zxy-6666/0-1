## 0. 本轮迭代（2026-08-29 第5轮）：安全站点模型（正向贪心优先 + Q-time 入口前瞻）

### 0.1 用户逻辑（"安全站点"）

- **安全站点** = Q-time 区间前的 step（如 PLASMA→DISPENSE 4h Q-time，PLASMA 即安全站点）。
- **核心规则**：做完当前站点就继续往下做（机台空闲且 step 要做就直接做，越早越好）；
  只有遇到 Q-time 区间（进入 start_step 前）才额外考虑"要不要进去"；
  不要倒着排导致前面设备空闲而没做（如 FTF-INPUT-BANK 02:05 完成、FTF-OPUT-FTF 14:57 才开始）。
- 约束（手动调整 delay/pin、reference 释放、粗排锚点）是硬性下界，不能与新逻辑打架。

### 0.2 改动 1：删除"异常间隙"告警（用户点名删除）

`_detect_schedule_anomalies` 中"相邻步骤异常等待间隙"检测整块删除（保留引用环检测与
引用配置错误检测）。该告警只提示不改变结果，且把物理设备竞争的等待误报为"不合理拖后"。

### 0.3 改动 2：整链块"正向贪心优先"（安全站点模型核心）

`_precompute_whole_chain_block`（整链块调度）开头新增正向贪心尝试：
- 从链首（安全站点）开始，逐步骤沿链正向贪心找最早槽位（模拟真实占用）；
- 每步下界 = max(上一步结束+步间等待, 该步硬性下界[锚点/reference释放/manual])；
- 链内 Q-time 全部达标且步骤顺序合法 → 直接采用（所有步骤尽量早开始）；
- **pending reference 检查**：链内步骤被"未释放且无预测锚点"的引用阻塞时放弃贪心
  （释放时刻未知，贪心早做会 reference 违背），回退原逻辑；
- 不达标（紧链/设备竞争挤散）→ 回退原"倒排 + 整链后移"保底（紧凑不超 Q）。

效果：宽松预算链（如 A006-D1 FTF 段 10080min）不再被倒排整体推迟，中间步骤做完即走；
仅紧链/设备竞争场景保留倒排保底。**良性 fuzz Q-time 超时条目 7314 → 3547（减半）**。

### 0.4 改动 3：Q-time 前瞻感知 pin/delay（test_pin_linkage 8/9→9/9）

`_tight_qtime_target_start` 估算端步骤 E 的可行开始时刻时，把 E 的 manual_adjust（delay）
与 pin 约束并入 e_base（E 不早于 pin/delay 时刻）。此前前瞻不感知 pin：pin 把
PC2.UF-DISPENSE 钉到 22:00（实际被设备推到次日 09:30），PLASMA（安全站点）延迟不足 →
PLASMA→DISPENSE 超 498min。修复后安全站点延迟足量，test_pin_linkage 恢复 9/9。

## 0a. 上轮迭代（2026-08-29 第4轮）：fuzz 验证修复 + 引用释放下界钳制

### 0.1 触发背景

用户要求"跑几千个算例"验证算法。本轮新增 `tools/fuzz_scheduler.py`（基准 seed 20260828，
非良性/良性两种模式）共发现并修复 4 类逻辑漏洞，全部落地 `scheduler.py`。

### 0.2 Fix4：停机窗 3 元组 tagged（只约束操作起点）

**现象**：fuzz seed 20260828001 出现 real2 DISPENSE→CURE 527595min 超时（排到 2027 年）。

**根因**：qty=25 的 FC-REFLOW CT≈925min 超过每日 08:30-22:00 停机窗 810min。原 `_find_earliest_slot`
要求操作完整时长不跨越停机窗 → 找不到槽位 → 被推到 365 天窗口末尾。

**修复**：`machine_intervals` 停机窗改为 3 元组 `(s, e, "down")`：
- `_skip_unavailable` / `_find_earliest_slot` / `_find_latest_slot` 对 `tag=="down"` 只检查
  **操作起点**不得落在窗内（在则推到窗口结束），允许长 CT 操作跨越停机窗继续运行；
- 普通占用区间仍要求完整时长不重叠（分离 down / occupied 两个列表处理）。

**验证**：seed 20260828001 非良性最晚结束 2026-09-06 16:34（不再有 2027 条目）。

### 0.3 缺失步骤修复（never_release_keys 预释放 + 死锁环处理）

**现象**：非良性 3000 例每 lot 缺 70~100 步。

**根因**：三类引用永远不会被释放，下游无限等待 → all_blocked 死锁 break：
- (a) 引用源 lot 不在本轮排程列表（外部 lot）；
- (b) 源已越过引用步骤（current_step 后移扰动）；
- (c) 源 target_step 截断在引用步骤之前。
另有一类真·死锁环（如 PC2 首步等 real2.DAF-SAT、real2 等 PC2.FC-REFLOW）。

**修复**：
- 调度初始化时预释放 (a/b/c) 三类引用（release 基于 schedule_start/源 start_time + start_mod 偏移）；
- 死锁环按**连通分量**判定真·死锁（任一 lot 首步被同分量引用阻塞）才启用预测释放，
  收敛环（PC1↔real1）不预测，避免引用违背；
- 主循环 all_blocked 时用"源粗排锚点 + CT"预测释放放宽后继续循环，不再直接 break。

**验证**：缺失步骤 3000 例 **0**（稳定）。

### 0.4 成员硬截止误排除修复

**现象**：real2 的 CURE 就绪 09:05 < 批次实际开炉 14:45，却被"晚于截止 08:02"错误排除
→ real2 单开一炉，DISPENSE→CURE 超 Q 240min。

**修复**：`_compute_batch_slot` 仅当 `est > hard_deadline and est > batch_start` 才排除成员
（成员晚于截止但早于批次实际开炉时并入不改变开炉时刻，放行共炉）。

### 0.5 引用释放下界钳制（本次会话新增）

**现象**：良性 fuzz 64 例引用违背，典型模式 real1.UF-DISPENSE（08/19 12:22）早于
PC1.UF-DISPENSE 释放（08/19 13:46，PC1 qty=25 CT≈914min）。

**根因**：`_try_schedule_chain_forward` 链内逐步骤放置（前缀循环 + 回退循环）非首步用
`ready_time = lot_entries[-1].end_time`，**未应用已释放 reference 的释放时刻下界**——
主循环单步路径经 `_update_blocked_ready_time` 处理，链路径漏了；释放后 ref 移出 pending_refs，
链路径的 pending 检查也不再拦截。

**修复**：两处逐步骤放置点（`scheduler.py` 约 2160/2480 行）在 ready_time 计算后追加：
对 `i >= ref_block_info[ref_key]` 且 `ref_release_times` 中已有的释放时刻，取 max 钳制。

**验证**：良性 3000 例引用违背 **64 → 0**；非良性 3000 例 **239 → 206**（余量均为
非良性扰动制造的数据固有矛盾：current_step 后移/target 截断/预算收紧产生的互锁死链）。

### 0.6 两遍取优四元组

`_count_missing_steps` / `_count_ref_violations` 加入择优：比较
`(缺失步骤数, 引用违背数, Q-time条目数, 总超时分钟)`，缺失步骤最硬性（丢步的排程无论
Q-time 多优都非法）。两遍取优保证回喂预测不劣化第一遍结果。

## 1. 上轮迭代（2026-08-28 第1轮）：手动调整场景 Q-time 修复

### 1.1 目标与成果

修复手动调整（manual adjust）场景下恒组批（PKPOV001 together=true）Q-time 拉爆：

| 场景（tools/diag_issue2_tmp.py） | 提交版（08-28 14:00） | 本轮修复后 |
|---|---|---|
| 基线（无手动调整） | 0 超时 | 0 超时 |
| delay real1 UF-CURE ≥ 08/18 20:00 | PC1 超616min / real1 超503min | **0 超时** |
| pin real1 UF-CURE @ 08/18 20:00 | PC1 超616min / real1 超503min | **0 超时** |
| delay real1 FC-REFLOW ≥ 08/17 20:00 | PC1 PLASMA 超1079min 等 | 仍超时（见 0.4） |

### 1.2 根因（本轮修掉的 bug）

- `_compute_batch_slot` 用**全局推进时钟 `now`** 作为批次最早开炉下限：
  `open_time = max(ready_time, now)`。
- 其它 Lot 的远未来锚点步骤（如 real1 的 UF-PLASMA 锚点被 CURE 手动延迟推到 17:56）
  会把 `now` 抬到本 Lot 就绪之后数小时；本 Lot 被选中时批次以 `now` 开炉 → Q-time 超限
  （实测 PC1 的 CURE 就绪 10:18、deadline 14:08，却因 `now=18:03` 开炉超时 235min）。

### 1.3 修复

- 改为 `open_time = max(ready_time, 设备实际空闲时刻)`：设备实际空闲时刻 = `bs["busy_until"]`
  （上一批次结束时刻；None 表示设备从未占用/已空闲）。
- 运行中的批次已被 `busy_until` 守卫（L1230-1232 `if busy_until: return False`）拦截，
  因此走到 open_time 时设备必然空闲，取 ready_time 即可，不再受全局 `now` 抬升影响；
  批次可回溯到该 Lot 真实就绪时刻开炉，不被无关 Lot 的锚点拖累。
- 顺带移除上一轮遗留的 `SCHED_TRACE_BLOCK`（PC1/real1/PC2/real2 硬编码名）调试打印。

### 1.4 已知边界（未修复，供下次迭代）

- **delay real1 FC-REFLOW ≥ 08/17 20:00 仍超时**：
  PC1 BAKE→DISPENSE 923min / PLASMA→DISPENSE 1079min / PC2 DISPENSE→CURE 228min /
  real2 DISPENSE→CURE 112min。
  - 根因链：PKCON/PKFCV 设备 22:00-08:30 停机窗 → real1 的 FC-REFLOW（手动延迟 ≥20:00）
    当晚无法放满 125min，被推到次日 09:30 → real1 的 UF-BAKE 实际 04:51（08/19）才开，
    其粗排锚点却停在 08/18 10:15（锚点未计入设备停机窗）→ PC1 的 UF-DISPENSE（引用
    real1 的 BAKE）被实际钉到 09:30（08/19），而 PC1 自己的 BAKE/PLASMA 已按过早锚点

## 2. 本次迭代目标

解决 **UF-CURE 设备（PKPOV001 单台）在恒组批/并行模式下 Q-time 超时**，并实现真正的"恒组批等待凑批"：

- **together=true（恒组批）**：到达同一"批次步骤"（如 UF-CURE）的多个 Lot，在等待窗口内合并进同一次炉（最多 max_lots/max_qty）。先到者等后到者一起开炉。
- **together=false（并行/多槽）**：到点即入，允许并行重叠（受 max_lots/max_qty 限制），不独占设备、无需互斥。

## 3. 根因（本次修掉的 4 个 bug）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 恒组批从不合并（每炉只装一个 Lot），单机串行拉爆 Q-time | `_compute_batch_slot` 成员扫描只检查其它 Lot 的**当前步骤**是否已是 CURE；跨 product 还要求 step_name 精确相等 → 永远匹配不上 | 重写成员扫描：沿其它 Lot 的 remaining 找前方第一个"同批次步骤"（同 product=精确同名；跨 product=**工艺后缀 + stage 相同**），预估到达时间，窗口内并入 |
| 2 | 批次重叠 / 等待 Lot 永久阻塞 | busy_until 判定用了 Lot 陈旧 `ready_time`；且 pending 块之后缺"设备运行中禁止新开批次" | 新增 `cur_time` 参数（取调度器真实推进时间）；pending 块之后加 `if busy_until: return False`，运行中禁止新开批 |
| 3 | 链部分调度后 CURE 整步丢失（步骤重复/跳步） | 主循环在 CFW（正向整链）部分成功后落单步时，仍用**陈旧的 step 变量**（链首），重复记录已排步骤并跳过端步骤 | 主循环：CFW 返回 `scheduled_count>0` 但未完成时 `continue` 重新拾取，让下一轮以更新后的 step_index 处理端步骤 |
| 4 | 批次落在上一批运行期间（并发超容量） | 新批次开炉时间用陈旧 `ready_time`（如 21:00），而设备要等到 01:12 才空闲 | `open_time = max(就绪, 设备空闲时刻)`，批次从 `max(ready_time, now)` 起开 |
| 5 | 晚拾取成员错过同批（reference 阻塞场景） | 成员因 reference 阻塞晚于 cur_time 才被拾取，此时 `now >= busy_until` 恰好触发"批次过期清理"，pending 成员资格被误清 | **pending 成员加入判定先于批次过期清理**：成员就绪 ≤ 批次开始 → 仍并入同批 |

## 4. 关键函数与位置（scheduler.py）

- `_compute_batch_slot(eqp_id, lot, step, ct, ready_time, spec, lot_state, ..., cur_time)` — 恒组批批次槽位/凑批核心。逻辑要点：
  1. 先判定 pending 成员加入（`lot_name in pending.members and ready <= pending.start`）；
  2. busy_until 运行中禁止新开批；
  3. 新批 `open_time = max(ready_time, cur_time)`；
  4. 成员扫描（suffix+stage 匹配、预估到达、`est <= open_time + wait_window`、容量 max_lots/max_qty）；
  5. 记录 pending 供后到成员加入。
- `_check_special_eqp_available(eqp_id, ...)` — together=false 并行容量检查（active 列表按 max_lots/max_qty）。
- `_register_special_eqp_usage(...)` — 提交批次占用（together=true 设 busy_until；false 独立追踪）。
- `_is_parallel_eqp(eqp_id, special_eqp_map)` — together=false 判定。
- 主循环（`schedule()` 内）：恒组批设备走 `_compute_batch_slot`；并行设备走 `_check_special_eqp_available` + `avail=ready`；特殊设备不写排他 `machine_intervals`。
- 常量：`BATCH_WAIT_WINDOW = 240`（凑批窗口）、`TIGHT_CHAIN_DEFER_MAX = 10`（紧链终止保护）。

## 7. 已知边界 / 注意事项

1. **人工超载不可解**：8 个同 product lot 抢单台 5.5h 炉 + 240min DISPENSE→CURE 窗口，数学上不可全部满足，部分 Lot 必然超 Q-time（属数据约束问题，非代码 bug）。
2. **历史 defer 启发式**：主循环"全链设备可通行性前瞻 + defer"在瓶颈端设备（如 PKPOV001 忙）时会过度推迟整条链，base `schedule()` 在重负载/强 reference 约束下可能把后到 Lot 推很远；但生产路径 `schedule_optimized`（多 seed 择优）能修正到最优（如 real2/PC2 从 18:08 优化到 12:29）。若后续要改，重点在 defer 条件应只对"中间步骤积压"生效、不应因端设备忙整链 defer。
3. **跨 product 共炉匹配**：按 `step_name 后缀 + stage_name` 匹配（如 UF-CURE 的 suffix=CURE、stage=AB1-UF），避免 DAF-CURE 误配到 UF-CURE。若同一 stage 内存在同名后缀的多个步骤，需在后续迭代补充更精确的匹配规则。
4. **环境变量调试开关**：`scheduler.py` 保留 `SCHED_TRACE=1`（主循环 DEFER/TRACE 打印）与 `QFAIL`（Q-time 链失败诊断）两个环境变量控制的调试打印，均为可选诊断、不影响逻辑。历史 QDBG 打印（含 PC1/real1 硬编码名）已在本轮清理中移除。
