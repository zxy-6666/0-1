## 0.1 第20轮（2026-09-03）：lead 先导批硬约束 + 纯完工目标 + 组批机前瞻修复

> 本轮横跨多次需求变更，直接对接下来的"换模型续跑"最重要的是**当前代码状态**、**用户核心诉求**与**遗留问题**，已在下文集中说明。

### 1. 版本决策（已定，勿再改回）

- 用户上传了 **v1.0 快照**（`半导体高优先级批次自动排程v1.0.zip`，已解压在本地核对过，未覆盖代码）。

- 逐文件 diff 结论：**当前版 = v1.0 + 本轮全部改动**（v1.0 无 pioneer/闸B/纯完工目标，lead 仅闸A 且回拉阈值 2min、目标含 Q 缺口 1e6 重罚）。

- **用户选择：保留当前版为基**（不回退 v1.0）。详细对照见 `.trae/documents/version-diff-v1-vs-current.md`。

- 实测同算例：v1.0 不超Q 但先导批语义失效（real4.MD-MOLDING 反超 f45，闸A 2 例）；当前版先导批正确但 Q 会破——本轮修的就是这个窟窿。

### 2. 用户核心诉求（最终版）

1. **lead = 先导批(f 系)先行、正式批(real 系)尾随**：先导批先完成衔接步，正式批须在其后**冗余带内**开始。这是**硬约束**（不是权重）：默认 1.5h，可调，超了就是问题。
2. **总优化目标**：所有批次都排上、总（加权）完工时间最短。
3. **不要超Q**：不为攒 Q 余量把批次往后推好几天；设备占用时按"当前排队设备的完工时刻"安排，特别是连续 Q-time A→B→C：做 A 前先看 B/C 是否放得下，否则往后顺延到"三站首次同时可行"。
4. 先导批的 delay 完全不影响目标（不计完工得分），但 Q-time 等硬约束照常。

## 0.1 第19轮（2026-09-03）：数据管理「是否生效」逐行勾选

### 1. 用户需求

有些约束/配置（设备约束、Q-time、特殊批次步骤等）暂时用不上，但**删除后重新增加很麻烦**，
希望数据管理界面直接用「勾选」停用某一行：该行仍保留在 CSV 中，只是排程加载时被忽略；需要时重新勾选即可恢复。

### 2. 方案（用户确认）

- **适用范围**：除 `flow.csv`、`step_ct.csv` 外的**全部数据表**都支持逐行「是否生效」；
  flow / step\_ct 为主数据，不支持停用，避免破坏流程/工序引用完整性。

- **记录方式**：每张受支持的表新增一列 **`是否生效`**，勾选=`1`，未勾选=`0`；默认全部勾选生效。
  支持的表：`ftf_qty_change.csv`、`priority_wait.csv`、`qtime.csv`、`shift_change_time.csv`、
  `shift_config.csv`、`eqp_constraint.csv`、`lot_list.csv`、`lot_constraints.csv`、
  `manual_adjust.csv`、`special_lot_step.csv`、`step_time_window.csv`、`special_eqp.csv`。

### 3. 改动

- **后端** **`data_loader.py`**：`_read_csv` 统一调用新增的 `_apply_enable_filter(df)`——
  若表含 `是否生效` 列，则过滤掉取值为停用集合（`0/否/n/no/false/off`，忽略大小写与首尾空格）的行；
  空值视为生效（默认勾选）。因所有约束加载函数（load\_qtime、load\_eqp\_constraints、load\_lot\_constraints、
  load\_special\_lot\_step 等）都经 `_read_csv`，故过滤对全部支持表自动生效，未来新增表也自动获得该能力。

- **前端** **`web/templates/index.html`**：

  - 新增 `ENABLE_COL` / `ENABLE_SUPPORTED` 常量与 `ensureEnableColumn()`（加载/上传受支持表时自动注入
    `是否生效` 列，默认 `1`）。

  - `renderCell` 对 `是否生效` 列渲染勾选框；`collectData` / `input` 事件处理勾选框读取（勾选存 `1` 否则 `0`）；
    新增行默认勾选；新增 `td.col-enable` 样式。

- **前端下拉联动 Bug 修复（lot\_list / lot\_constraints step 下拉只能保持一个）**：
  动态下拉（`DYNAMIC_OPTIONS`）使用 `datalist`，原实现给所有行生成**同一个** `id`
  （`dl_dyn_lot_list_csv_step_name`），浏览器只取文档中第一个 datalist，导致每行下拉
  不随本行 `product_name` / `lot1` / `lot2` 变化。修复：`renderCell` 新增 `rowIdx` 参数，
  为每行生成唯一 datalist id（`..._step_name_r<行号>`），并在 `renderTableBody` 传入 `origIdx`。
  `lot_list`（step\_name/target\_step←product\_name）与 `lot_constraints`（step1←lot1、step2←lot2）
  同时修复。

## 0.1 第18轮（2026-09-02）：调度器余量感知放置 + 超Q修复余量锚定 + 跨班次整体后移

### 1. 用户反馈（本轮）

- "1. 你仍然会把一些批次因为Q-time会超时仅仅只刚好排在Q-time的极限时间，导致最终的Q-time余量是1min。
  实际上你需要根据我设置的Q-time余量需求尽量往那上面靠，这是Q-time即能保证有剩余量，又能保证能尽早做的方案。
  而且，当前的目标函数的惩罚好像没起作用，Q-time起点站点不会有那种变化"

- "2. 紧链跨班次你能识别你就把紧链整体后移就好了，不要让紧链开始就在交接班的时候。"

### 2. 根因定位（第18轮，已确认）

- **"余量 1min"根因**：`_fix_qtime_overflow_pull_chain_start`（超Q后链首后移修复）把链首移到
  `a_ref_min = b_ref - 预算 + 1min` → 跨度恰好 D-1 → **余量恒为 1min**；且与用户安全余量参数无关
  （无论设多少，修复都只留 1min），导致优化器无论怎么换参数，起点站都不变（"罚分没起作用"）。

- **跨班次根因**：同一修复把链首后移时只看设备槽，不校验班次——把链首甩进上一班次（如 PLASMA
  挪到 06:04 夜班、DISPENSE 仍 09:30 白班）→ 紧链跨班次告警。

- **整链块路径余量缺口**：`_precompute_whole_chain_block` 正向贪心只校验 span ≤ D，E 被设备
  顶到极限（span≈D-1）时也直接采用 → 起点站不变、余量不随安全余量参数变化。

- **单步前瞻估算缺口**：`_tight_qtime_target_start` 的 e\_ready 未计入中间步骤设备占用，
  E 实际落点比估算晚 → 链首延迟不足、余量被侵蚀。

### 3. 修复（scheduler.py）

- **a) 超Q修复按安全余量锚定**：`_fix_qtime_overflow_pull_chain_start` 目标跨度改为
  `预算 - _q_target_margin(q)`（紧链余量目标 = max(预算×%, 下限)，松链不设），
  链首移到 `b_ref - (D - safe)` → 余量 ≈ safe（不再 1min），起点随安全余量参数变化。

- **b) 超Q修复跨班次整链后移**：后移目标若落在 B 所在班次的紧邻前一班次（跨班次），
  优先把链首推到 B 所在班次起点（经 `_skip_shift_change` 跳过交接窗，链首不落在交接班）；
  推后越序（A 越过 B）则放弃跨班次对齐，保留余量锚定后移（跨班次由告警提示）。
  schedule() 调用点补充展开 `shift_change_intervals` 传入。

- **c) 整链块余量感知**：`_precompute_whole_chain_block`：

  - 正向贪心校验 span ≤ D - safe（不达标回退倒排——倒排把链首拉回贴近 E，余量恢复）；

  - 倒排校验同样按 D - safe；收敛（max\_gap==0）后链已紧凑、span 为固有长度时，余量缺口
    视为"最佳余量"直接采用（避免无谓整链平移 + 触发 defer 级联）；

  - 倒排新增跨班次校验：紧 Q 对窗口跨班次 → 把链首推到班次起点（cs\_target 分支）。

- **d) 单步前瞻 e\_ready 计入中间步设备占用**：`_tight_qtime_target_start` 沿链逐步用
  `_find_earliest_slot` 模拟中间步骤真实槽位（与单步调度一致），E 估算不再乐观。

- **e) 跨班次设备守卫放宽**：`_tight_qtime_target_start` 的跨班次推后不再要求 S 恰好卡在
  班次起点（+5min），改为"S 在目标班次内（早于下一班次边界）有可用槽即可"——避免因设备
  在边界时刻被占就放弃整体后移（用户"整体后移就好了"）。

- 新增 `_q_target_margin(q)`：紧 Q 余量目标（分钟）= max(预算×QTIGHT\_SAFETY\_MARGIN%, QTIGHT\_MIN\_MARGIN)。

### 5. 遗留

- 跨班次告警在"链内两段紧 Q 互斥 + 端步骤被批次钉晚"（如 PC1 型）场景仍不可避免——

## 0.1 第17轮（2026-09-02）：Q-time 余量统一计量 + 校验错误明细展示

### 1. Q-time 余量统一计量（validation.py compute\_objective，最终方案）

- 演进：第16轮"固定40%收益曲线" → 第17轮前段"安全余量参考点收益 + 梯度罚分 + 硬门槛" →
  **最终版：余量与加权完工时间统一计量**（用户："之前设计分开了，且硬门槛不利于迭代搜索"）。

- 公式（单位分钟，直接并入 score，连续可导）：

  - 达标区（rel = margin/safe ≥ 1）：微奖励 `-20 × (1 - 1/rel)` 分钟/链（渐近饱和，"得分很少"）；

  - 缺口区（rel < 1）：重罚 `强度 × 100万 × (1-rel)³` 分钟/链，越接近 0 越大，
    rel=0 时 ≈ 一次超Q违规（\_PENALTY\_PER\_ERR=1e6）的量级 → 罚分再也不可能被完工时间盖过。

- `safe = max(预算×安全余量%, 安全余量下限)`；`qtime_shortfall_gradient`（默认3）为罚分强度参数。

- compute\_objective 返回：`qtime_margin_term`（统一余量项，正=罚、负=奖）、
  `qtime_margin_violations`（低于安全余量的链明细）、min\_qtime\_margin / \_ratio / \_benefit（展示+同分次目标）。

- 已移除：qtime\_margin\_shortfall / qtime\_margin\_penalty / qtime\_margin\_ok（旧设计残留）。

### 2. 优化器得分（optimizer.py）

- 合法解 `penal = obj["score"] + obj["qtime_margin_term"]`（主循环 + SA 一致），比较恢复为
  **纯得分优先 + 同分比余量收益**（已撤掉硬门槛分类，搜索连续）。

- 兜底：最优合法解仍有余量低于安全余量的链时，输出醒目告警（warning + schedule\_warnings，
  列出明细），同时得分会明显变大（几十万级）——直观提示"余量未达标"。

- **用户场景**：长 Q-time（如 BAKE→DISPENSE 1440min）的链首被自然排得过早，端步骤被
  手动延后/设备挤兑推晚后整段超 Q（real1 1445min>1440min），但链首之后有大段空缺。

- **修复策略**（尽力而为，schedule() 两遍择优 + lead\_back\_shift 之后调用）：

  1. 遍历"超时" Q-time 告警，定位链首 A 与端步骤 B；
  2. 合规条件：a\_ref ≥ b\_ref - 预算（**注意方向：链首越早间隔越大越易超时**；
     **参考点：start\_mod 决定 A 侧、end\_mod 决定 B 侧**）；
  3. 用设备占用区间找 ≥ (A.start + 需后移量) 的最早可用槽（\_find\_earliest\_slot），
     保序（A 不得越过 B）；
  4. 上一步约束（后移不得早于上一步完成）+ 上游 Q 保护（A 作为 end 的链不得撑爆）；
  5. 同步更新 lot/设备维度 entry，告警标记 OK；
  6. 全部尝试后统一 validate 复查：违规数增加则整体回滚。

- **效果**：test\_28 从 4 项错误（real1 BAKE + PC2 DISPENSE 各 2 条）降到 2 项（仅 PC1
  DISPENSE→CURE，因 PLASMA→DISPENSE 240min 紧链约束，后移 DISPENSE 会撑爆上游，
  保守放弃——属真实约束冲突）。

- **链式后移尝试结论（已回退）**：针对 PC1 实验了"链式传播逐层后移"——整链精确平移
  撞设备占用（PC1 DISPENSE 设备槽被其他 lot 排他占用 10:13-11:19）、且参考点错位

  - 链内间隔再校验"的混合方案，风险较高，非必须勿动\*\*。

## 0.3 第11轮（2026-09-01）：打分体系三改（用户三需求）

### 1. 优先级权重差 ≤10%（validation.py compute\_objective）

- 原 `w = 1 + (max_ext - ext)`（1-1 与 4-1 差 300%）→ `w = 1 + 0.1×(max_ext−ext)/span`，
  span=max(1, max\_ext−1)。实测：1-1→1.10、最高级→1.00，任意两优先级差 ≤10%。

### 2. 次目标改为"归一化余量比率"（validation.py）

- 新增 `min_qtime_margin_ratio = min(margin/budget)`：不同长度 Q 段在同一尺度可比，
  避免绝对分钟天然偏袒长段（1440min 段余量分钟天然大）。绝对分钟 `min_qtime_margin`
  保留供 web/报表展示。优化器 tie-break 改用比率。

### 3. Q-time 超时软约束引导搜索（optimizer.py）

- 非法解不再直接丢弃：`penal = 1e9 + 错误数×1e6 + 1.0×总超时分钟`。
  1e9 保证合法解永远优于非法解；但非法解间按（错误数→超时量）可比较 → 搜索
  在无合法解时也朝"违规更轻"收敛。

- 外层 best 统一承载合法/非法（原 best\_violating 兜底删除，降冗余）；
  细调层 \_eval\_solution 非法邻域返回罚分 obj，SA 在软约束引导下可找到合法解。

- 收敛对非法解也生效（early\_stop=15 / refine\_patience=20），不再跑满。

### 0.2 根因

- 停机窗原语义只约束"操作起点不落在窗内"，允许长 CT 操作跨越停机窗继续运行 →

  real2 的 MD-MOLDING 因闸A（等 PC2.MD-MOLDING 完成）被推到次日 11:44，未背靠背。

### 0.3 修复 1：停机窗"完整时长不跨越"（scheduler.py）

- 新增 `_down_fit_span(down)`：停机窗之间最大可用间隙（`timedelta.max` 若少于 2 窗口）。

- 新增 `_down_push(c, duration, down, can_fit)`：判断 `[c, c+duration)` 与停机窗关系，
  返回应把起点推到的时刻（None=当前可用）。

- `_find_earliest_slot` / `_find_latest_slot` / `_skip_unavailable`：计算
  `can_fit = duration <= _down_fit_span(down)`——**时长放得进相邻停机窗间隙时，要求完整
  时长不跨越停机窗**（不满足则整体推到窗后）；仅当操作时长超过最大可用间隙（长 CT，
  如 qty=25 的 FC-REFLOW CT≈925min > 每日可用段 810min）退化为只约束起点。

- 语义与用户要求一致：**链整体后移 → 落到最早可用位置**（窗后起点即最早可放位置）。

### 0.4 修复 2：E 可行性守卫（跨班次推后不撑破 Q 预算）

`_tight_qtime_target_start` 跨班次把链首 S 推后到班次边界时，必须校验"推后后 E（端步骤）

## 0b. 上轮迭代（2026-08-29 第5轮）：安全站点模型（正向贪心优先 + Q-time 入口前瞻）

### 0.1 用户逻辑（"安全站点"）

- **安全站点** = Q-time 区间前的 step（如 PLASMA→DISPENSE 4h Q-time，PLASMA 即安全站点）。

- **核心规则**：做完当前站点就继续往下做（机台空闲且 step 要做就直接做，越早越好）；
  只有遇到 Q-time 区间（进入 start\_step 前）才额外考虑"要不要进去"；
  不要倒着排导致前面设备空闲而没做（如 FTF-INPUT-BANK 02:05 完成、FTF-OPUT-FTF 14:57 才开始）。

- 约束（手动调整 delay/pin、reference 释放、粗排锚点）是硬性下界，不能与新逻辑打架。

### 0.2 改动 1：删除"异常间隙"告警（用户点名删除）

`_detect_schedule_anomalies` 中"相邻步骤异常等待间隙"检测整块删除（保留引用环检测与
引用配置错误检测）。该告警只提示不改变结果，且把物理设备竞争的等待误报为"不合理拖后"。

### 0.3 改动 2：整链块"正向贪心优先"（安全站点模型核心）

`_precompute_whole_chain_block`（整链块调度）开头新增正向贪心尝试：

- 从链首（安全站点）开始，逐步骤沿链正向贪心找最早槽位（模拟真实占用）；

- 每步下界 = max(上一步结束+步间等待, 该步硬性下界\[锚点/reference释放/manual])；

- 链内 Q-time 全部达标且步骤顺序合法 → 直接采用（所有步骤尽量早开始）；

- **pending reference 检查**：链内步骤被"未释放且无预测锚点"的引用阻塞时放弃贪心
  （释放时刻未知，贪心早做会 reference 违背），回退原逻辑；

- 不达标（紧链/设备竞争挤散）→ 回退原"倒排 + 整链后移"保底（紧凑不超 Q）。

效果：宽松预算链（如 A006-D1 FTF 段 10080min）不再被倒排整体推迟，中间步骤做完即走；
仅紧链/设备竞争场景保留倒排保底。**良性 fuzz Q-time 超时条目 7314 → 3547（减半）**。

### 0.4 改动 3：Q-time 前瞻感知 pin/delay（test\_pin\_linkage 8/9→9/9）

`_tight_qtime_target_start` 估算端步骤 E 的可行开始时刻时，把 E 的 manual\_adjust（delay）
与 pin 约束并入 e\_base（E 不早于 pin/delay 时刻）。此前前瞻不感知 pin：pin 把
PC2.UF-DISPENSE 钉到 22:00（实际被设备推到次日 09:30），PLASMA（安全站点）延迟不足 →
PLASMA→DISPENSE 超 498min。修复后安全站点延迟足量，test\_pin\_linkage 恢复 9/9。

### 0.3 缺失步骤修复（never\_release\_keys 预释放 + 死锁环处理）

**现象**：非良性 3000 例每 lot 缺 70\~100 步。

**根因**：三类引用永远不会被释放，下游无限等待 → all\_blocked 死锁 break：

- (a) 引用源 lot 不在本轮排程列表（外部 lot）；

- (b) 源已越过引用步骤（current\_step 后移扰动）；

- (c) 源 target\_step 截断在引用步骤之前。
  另有一类真·死锁环（如 PC2 首步等 real2.DAF-SAT、real2 等 PC2.FC-REFLOW）。

**修复**：

- 调度初始化时预释放 (a/b/c) 三类引用（release 基于 schedule\_start/源 start\_time + start\_mod 偏移）；

- 死锁环按**连通分量**判定真·死锁（任一 lot 首步被同分量引用阻塞）才启用预测释放，
  收敛环（PC1↔real1）不预测，避免引用违背；

- 主循环 all\_blocked 时用"源粗排锚点 + CT"预测释放放宽后继续循环，不再直接 break。

**验证**：缺失步骤 3000 例 **0**（稳定）。

### 0.4 成员硬截止误排除修复

**现象**：real2 的 CURE 就绪 09:05 < 批次实际开炉 14:45，却被"晚于截止 08:02"错误排除
→ real2 单开一炉，DISPENSE→CURE 超 Q 240min。

**修复**：`_compute_batch_slot` 仅当 `est > hard_deadline and est > batch_start` 才排除成员
（成员晚于截止但早于批次实际开炉时并入不改变开炉时刻，放行共炉）。

### 0.5 引用释放下界钳制（本次会话新增）

**现象**：良性 fuzz 64 例引用违背，典型模式 real1.UF-DISPENSE（08/19 12:22）早于
PC1.UF-DISPENSE 释放（08/19 13:46，PC1 qty=25 CT≈914min）。

**根因**：`_try_schedule_chain_forward` 链内逐步骤放置（前缀循环 + 回退循环）非首步用
`ready_time = lot_entries[-1].end_time`，**未应用已释放 reference 的释放时刻下界**——
主循环单步路径经 `_update_blocked_ready_time` 处理，链路径漏了；释放后 ref 移出 pending\_refs，
链路径的 pending 检查也不再拦截。

**修复**：两处逐步骤放置点（`scheduler.py` 约 2160/2480 行）在 ready\_time 计算后追加：
对 `i >= ref_block_info[ref_key]` 且 `ref_release_times` 中已有的释放时刻，取 max 钳制。

### 1.2 根因（本轮修掉的 bug）

- `_compute_batch_slot` 用**全局推进时钟** **`now`** 作为批次最早开炉下限：
  `open_time = max(ready_time, now)`。

- 其它 Lot 的远未来锚点步骤（如 real1 的 UF-PLASMA 锚点被 CURE 手动延迟推到 17:56）
  会把 `now` 抬到本 Lot 就绪之后数小时；本 Lot 被选中时批次以 `now` 开炉 → Q-time 超限
  （实测 PC1 的 CURE 就绪 10:18、deadline 14:08，却因 `now=18:03` 开炉超时 235min）。

### 1.3 修复

- 改为 `open_time = max(ready_time, 设备实际空闲时刻)`：设备实际空闲时刻 = `bs["busy_until"]`
  （上一批次结束时刻；None 表示设备从未占用/已空闲）。

- 运行中的批次已被 `busy_until` 守卫（L1230-1232 `if busy_until: return False`）拦截，
  因此走到 open\_time 时设备必然空闲，取 ready\_time 即可，不再受全局 `now` 抬升影响；
  批次可回溯到该 Lot 真实就绪时刻开炉，不被无关 Lot 的锚点拖累。

- 顺带移除上一轮遗留的 `SCHED_TRACE_BLOCK`（PC1/real1/PC2/real2 硬编码名）调试打印。

## 2. 本次迭代目标

解决 **UF-CURE 设备（PKPOV001 单台）在恒组批/并行模式下 Q-time 超时**，并实现真正的"恒组批等待凑批"：

## 4. 关键函数与位置（scheduler.py）

- `_compute_batch_slot(eqp_id, lot, step, ct, ready_time, spec, lot_state, ..., cur_time)` — 恒组批批次槽位/凑批核心。逻辑要点：

  1. 先判定 pending 成员加入（`lot_name in pending.members and ready <= pending.start`）；
  2. busy\_until 运行中禁止新开批；
  3. 新批 `open_time = max(ready_time, cur_time)`；
  4. 成员扫描（suffix+stage 匹配、预估到达、`est <= open_time + wait_window`、容量 max\_lots/max\_qty）；
  5. 记录 pending 供后到成员加入。

- `_check_special_eqp_available(eqp_id, ...)` — together=false 并行容量检查（active 列表按 max\_lots/max\_qty）。

- `_register_special_eqp_usage(...)` — 提交批次占用（together=true 设 busy\_until；false 独立追踪）。

- `_is_parallel_eqp(eqp_id, special_eqp_map)` — together=false 判定。

- 主循环（`schedule()` 内）：恒组批设备走 `_compute_batch_slot`；并行设备走 `_check_special_eqp_available` + `avail=ready`；特殊设备不写排他 `machine_intervals`。

- 常量：`BATCH_WAIT_WINDOW = 240`（凑批窗口）、`TIGHT_CHAIN_DEFER_MAX = 10`（紧链终止保护）。

## 7. 已知边界 / 注意事项

1. **人工超载不可解**：8 个同 product lot 抢单台 5.5h 炉 + 240min DISPENSE→CURE 窗口，数学上不可全部满足，部分 Lot 必然超 Q-time（属数据约束问题，非代码 bug）。
2. **历史 defer 启发式**：主循环"全链设备可通行性前瞻 + defer"在瓶颈端设备（如 PKPOV001 忙）时会过度推迟整条链，base `schedule()` 在重负载/强 reference 约束下可能把后到 Lot 推很远；但生产路径 `schedule_optimized`（多 seed 择优）能修正到最优（如 real2/PC2 从 18:08 优化到 12:29）。若后续要改，重点在 defer 条件应只对"中间步骤积压"生效、不应因端设备忙整链 defer。
3. **跨 product 共炉匹配**：按 `step_name 后缀 + stage_name` 匹配（如 UF-CURE 的 suffix=CURE、stage=AB1-UF），避免 DAF-CURE 误配到 UF-CURE。若同一 stage 内存在同名后缀的多个步骤，需在后续迭代补充更精确的匹配规则。
4. **环境变量调试开关**：`scheduler.py` 保留 `SCHED_TRACE=1`（主循环 DEFER/TRACE 打印）与 `QFAIL`（Q-time 链失败诊断）两个环境变量控制的调试打印，均为可选诊断、不影响逻辑。历史 QDBG 打印（含 PC1/real1 硬编码名）已在本轮清理中移除。
5. **stress test\_28\_manual\_adjust\_reschedule 已知边界（0.11 新增）**：手动延后链中步骤后整链重排，PC1 BAKE→DISPENSE(1440 宽松非相邻 Q) 超限、PC2 DISPENSE→CURE(240) 超限，优化器返「违规最少解」（4 错误、valid\_iterations=0），stress 稳态 **31/32**。已排查确认**非数学不可行**：PC1 保持手动目标 08/19 18:33 并把链首 UA-BAKE 后移到 08/19 即可全满足所有 Q；根因是**优化器搜索算子缺口**——手动 pin 感知下缺乏"整链回拉 + 链首后移以满足宽松非相邻 Q 预算"的移动，局部搜索在 3 种子 × 40/200/500 迭代下全部落到相同次优解（PLASMA 被推过夜至 08/20 06:51、链首 BAKE 停在 08/18）。结论：属待迭代的核心优化器链重排增强，非本次代码缺陷；修复需动核心运行器、回归风险高，本次按「记录结论不动代码」处理。
