## 2. 本次迭代目标

解决 **UF-CURE 设备（PKPOV001 单台）在恒组批/并行模式下 Q-time 超时**，并实现真正的"恒组批等待凑批"：

- **together=true（恒组批）**：到达同一"批次步骤"（如 UF-CURE）的多个 Lot，在等待窗口内合并进同一次炉（最多 max_lots/max_qty）。先到者等后到者一起开炉。
- **together=false（并行/多槽）**：到点即入，允许并行重叠（受 max_lots/max_qty 限制），不独占设备、无需互斥。

## 3. 根因（本次修掉的 4 个 bug）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 恒组批从不合并（每炉只装一个 Lot），单机串行拉爆 Q-time | `_compute_batch_slot` 成员扫描只检查其它 Lot 的**当前步骤**是否已是 CURE；跨 product 还要求 step_name 精确相等 → 永远匹配不上 | 重写成员扫描：沿其它 Lot 的 remaining 找前方第一个"同批次步骤"（同 product=精确同名；跨 product=**工艺后缀 + stage 相同**），预估到达时间，窗口内并入 |
| 2 | 批次重叠 / 等待 Lot 永久阻塞 | busy_until 判定用了 Lot 陈旧 `ready_time`；且 pending 块之后缺"设备运行中禁止新开批次" | 新增 `cur_time` 参数（取调度器真实推进时间）；pending 块之后加 `if busy_until: return False`，运行中禁止新开批 |
| 3 | 链部分调度后 CURE 整步丢失（步骤重复/跳步） | 主循环在 CFW（正向整链）部分成功后落单步时，仍用**陈旧的 step 变量**（链首），重复记录已排步骤并跳过端步骤 | 主循环：CFW 返回 `scheduled_count>0` 但未完成时 `continue` 重新拾取，让下一轮以更新后的 step_index 处理端步骤 |
| 4 | 批次落在上一批运行期间（并发超容量） | 新批次开炉时间用陈旧 `ready_time`（如 21:00），而设备要等到 01:12 才空闲 | `open_time = max(就绪, 设备空闲时刻)`，批次从 `max(ready_time, now)` 起开 |
| 5 | 晚拾取成员错过同批（reference 阻塞场景） | 成员因 reference 阻塞晚于 cur_time 才被拾取，此时 `now >= busy_until` 恰好触发"批次过期清理"，pending 成员资格被误清 | **pending 成员加入判定先于批次过期清理**：成员就绪 ≤ 批次开始 → 仍并入同批 |

## 4. 关键函数与位置（scheduler.py）

- `_compute_batch_slot(eqp_id, lot, step, ct, ready_time, spec, lot_state, ..., cur_time)` — 恒组批批次槽位/凑批核心。逻辑要点：
  1. 先判定 pending 成员加入（`lot_name in pending.members and ready <= pending.start`）；
  2. busy_until 运行中禁止新开批；
  3. 新批 `open_time = max(ready_time, cur_time)`；
  4. 成员扫描（suffix+stage 匹配、预估到达、`est <= open_time + wait_window`、容量 max_lots/max_qty）；
  5. 记录 pending 供后到成员加入。
- `_check_special_eqp_available(eqp_id, ...)` — together=false 并行容量检查（active 列表按 max_lots/max_qty）。
- `_register_special_eqp_usage(...)` — 提交批次占用（together=true 设 busy_until；false 独立追踪）。
- `_is_parallel_eqp(eqp_id, special_eqp_map)` — together=false 判定。
- 主循环（`schedule()` 内）：恒组批设备走 `_compute_batch_slot`；并行设备走 `_check_special_eqp_available` + `avail=ready`；特殊设备不写排他 `machine_intervals`。
- 常量：`BATCH_WAIT_WINDOW = 240`（凑批窗口）、`TIGHT_CHAIN_DEFER_MAX = 10`（紧链终止保护）。

## 7. 已知边界 / 注意事项

1. **人工超载不可解**：8 个同 product lot 抢单台 5.5h 炉 + 240min DISPENSE→CURE 窗口，数学上不可全部满足，部分 Lot 必然超 Q-time（属数据约束问题，非代码 bug）。
2. **历史 defer 启发式**：主循环"全链设备可通行性前瞻 + defer"在瓶颈端设备（如 PKPOV001 忙）时会过度推迟整条链，base `schedule()` 在重负载/强 reference 约束下可能把后到 Lot 推很远；但生产路径 `schedule_optimized`（多 seed 择优）能修正到最优（如 real2/PC2 从 18:08 优化到 12:29）。若后续要改，重点在 defer 条件应只对"中间步骤积压"生效、不应因端设备忙整链 defer。
3. **跨 product 共炉匹配**：按 `step_name 后缀 + stage_name` 匹配（如 UF-CURE 的 suffix=CURE、stage=AB1-UF），避免 DAF-CURE 误配到 UF-CURE。若同一 stage 内存在同名后缀的多个步骤，需在后续迭代补充更精确的匹配规则。
4. **环境变量调试开关**：`scheduler.py` 保留 `SCHED_TRACE=1`（主循环 DEFER/TRACE 打印）与 `QFAIL`（Q-time 链失败诊断）两个环境变量控制的调试打印，均为可选诊断、不影响逻辑。历史 QDBG 打印（含 PC1/real1 硬编码名）已在本轮清理中移除。
